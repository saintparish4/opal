# Framework compatibility

Does a project Opal installed build, pass its tests, and serve? Each framework's own starter project is installed with `opal install`, then built, tested, and started with that framework's own tools. [`benchmarks/BENCHMARKS.md`](../benchmarks/BENCHMARKS.md) covers how fast Opal installs; this file covers whether what it installs works.

## Method

The harness is [`frameworks.py`](./frameworks.py). For each scaffold it:

1. copies the scaffold into a fresh scratch folder and runs `opal install` there with an empty `OPAL_CACHE_DIR`, so every install is a cold one against the public registry;
2. runs up to three checks, each with a timeout:
   - **build**: `npm run build` has to exit 0 and leave its output behind;
   - **test**: `npm test` has to exit 0, for a scaffold that ships tests;
   - **runtime**: the production server is started through its npm script on a free port and polled until it answers HTTP 200, and then its whole process group is killed.

Every script runs through npm, using the `node_modules` Opal linked, because that is what a user does. Opal is only the installer here. Next.js and Astro telemetry and npm's update check are turned off, since they're network requests that aren't part of what's being checked. `TMPDIR` points inside the scratch folder, and the whole folder is deleted at the end.

### The scaffolds

Each one lives in [`frameworks/<name>/`](./frameworks/). It was generated once by the framework's own scaffolder at a pinned version, then committed without `node_modules`, a lockfile, or `.git`. Each has a `SCAFFOLD` file that gives the exact command, the scaffolder's version, the date, and anything changed afterwards. Running the scaffolders at harness time would make the matrix move with every scaffolder release. The scaffolds' version ranges still float, though, so the **Resolved** column records what each run actually installed.

| Scaffold | Generated by | build (output checked) | test | runtime (URL) |
|---|---|---|---|---|
| next | create-next-app 16.3.2 | `next build` (`.next/BUILD_ID`) | none | `next start` (`/`) |
| vite-react | create-vite 9.2.1, `react-ts` | `tsc -b && vite build` (`dist/index.html`) | none | `vite preview` (`/`) |
| vite-vue | create-vite 9.2.1, `vue-ts` | `vue-tsc -b && vite build` (`dist/index.html`) | none | `vite preview` (`/`) |
| astro | create-astro 5.2.6, `basics` | `astro build` (`dist/index.html`) | none | `astro preview` (`/`) |
| sveltekit | sv 1.1.1, `minimal`, TypeScript | `vite build` (`.svelte-kit/output`) | none | `vite preview` (`/`) |
| nest | @nestjs/cli 12.0.8 | `nest build` (`dist/main.js`) | `vitest run` | `node dist/main` (`/`) |
| express | hand-written | none | none | `node server.js` (`/health`) |

Some notes on individual scaffolds:

- **next:** its `package.json` is byte-identical to the one [`compare-pms.py`](../benchmarks/compare-pms.py) inlines, so the matrix and the benchmark install the same project.
- **sveltekit:** keeps the default `adapter-auto`. Outside a hosting platform, that adapter writes no deployment output, so the build is checked by `.svelte-kit/output`.
- **nest:** Nest 12's scaffold ships a vitest suite, not jest.
- **astro:** the preview server is started with `--ignore-lock`. Astro 7 moves `astro preview` into a detached background process when it detects a coding agent, and a detached process survives the kill. In a fresh copy there's no lock file for the flag to ignore, so all it changes is keeping the server in the foreground.

### The columns

- **Framework**: the scaffold, a folder under `frameworks/`.
- **Resolved**: the installed versions of the one or two packages that define the scaffold, read from `node_modules` after the install.
- **install**: `opal install` exited 0. The time is its wall time.
- **build**: `npm run build` exited 0, and the output named above exists.
- **test**: `npm test` exited 0.
- **runtime**: the server answered HTTP 200 within the timeout. The time runs from starting the npm script to the first 200.
- **Scripts skipped**: what Opal's install-scripts warning names. That means dependencies whose install scripts Opal didn't run, plus `project (...)` for the project's own lifecycle scripts. A pass in the other columns means the app worked without those scripts on these checks. It doesn't mean the scripts do nothing.

A cell reads one of four ways:

- `pass (time)`;
- `FAIL: reason`;
- `not run`, when a check it depends on failed (build and test need the install, and runtime needs the build);
- `-`, when the scaffold has no such check.

Failures stay in the table, and the harness exits non-zero if any cell failed. For every failed check, the JSON keeps the last 25 lines of its output.

The default timeouts are 900s for install, 900s for build, 600s for test, and 120s for runtime.

The times come from a single cold run over the public registry. They're there to spot something pathological, not to compare against other tools.

## Results: 2026-10-14, v0.4.0 baseline, before v0.4.1

This run is the baseline that v0.4.1 will be compared against. Opal is the `opal-linux-x64` asset from the [v0.4.0 release](https://github.com/saintparish4/opal/releases/tag/v0.4.0). The SHA-256 of the `opal` binary is `61595255213c9aeb7ef54a29a33604dc37540bf19a60f0fe8c8ab84c7af94540`, the same file BENCHMARKS.md's 2026-10-06 tables ran. The table committed for a release comes from that release's own asset.

Tool versions: opal 0.4.0, Node 24.19.0, npm 12.0.2. The machine is the laptop: AMD Ryzen 5 5625U (WSL limited to 8 of 12 threads), 16 GB RAM, Linux under WSL2. The whole run took 96s. Raw results: [`results/frameworks-20261014-210356.json`](./results/frameworks-20261014-210356.json).

### What this shows

- **All 21 checks passed:** 7 installs, 6 builds, 1 test suite, and 7 servers answering 200.
- **sveltekit:** Opal didn't run the project's `prepare` script (`svelte-kit sync || echo ''`), and the build and preview passed anyway. This matches the release plan's expectation that SvelteKit's Vite plugin runs the sync itself during a build. Only the build and the preview server were checked. The dev server and `npm run check` weren't, though `check` runs `svelte-kit sync` in its own script.
- **next:** Opal skipped one install script, `unrs-resolver`'s `postinstall` (`node postinstall.js`). `unrs-resolver` reaches the tree through `eslint-config-next`'s import resolver (`eslint-import-resolver-typescript`), and the matrix doesn't run `npm run lint`. So this run says nothing about whether that script mattered.

## Reproducing

```sh
python3 compat/frameworks.py --opal ~/opal-bench/v0.4.0/opal                     # all seven
python3 compat/frameworks.py --opal ./opal sveltekit nest                        # a subset
python3 compat/frameworks.py --opal ./opal --timeout build=1800,runtime=300      # longer timeouts
python3 compat/frameworks.py --opal ./opal next --keep                           # keep scratch to debug
```

You need:

- Python 3.9+;
- network access, for the registry and for the Google fonts that Next.js's build downloads;
- `node` and `npm` on `PATH`.

**Scratch:** the harness works in a fresh `opal-compat-*` folder in the system temp folder (`--work` puts it somewhere else) and deletes it at the end unless you pass `--keep`.

**Output:** it prints the markdown table above and writes the JSON to `compat/results/` (`--results` sends it elsewhere), along with the node, npm, and opal versions and the opal binary's path and SHA-256. A run is refused when the binary is in the temp folder and the results would go into the repository. The binary's path is recorded, so put it somewhere you're happy to publish.

## Regenerating or adding a scaffold

To regenerate a scaffold:

1. Run the command in its `SCAFFOLD` file, in an empty folder, with no TTY.
2. Delete `node_modules`, any lockfile, and `.git` if the scaffolder made them.
3. Replace `frameworks/<name>/` with the result.
4. Update the date and versions in `SCAFFOLD`.

A new scaffold is a new matrix: add a new dated table and keep the old one.

To add a framework, add its folder and `SCAFFOLD` file, plus an entry in `FRAMEWORKS` in `frameworks.py` naming its build script, the output to check, its server script and arguments, and the URL path to poll.

The repository's root `.gitignore` ignores every `public/` folder, so [`compat/.gitignore`](./.gitignore) re-includes them for the scaffolds' static assets. Check with `git status --ignored compat` that a new scaffold's files are all visible to git.
